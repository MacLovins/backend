## 1. Твоя зона

Ты делаешь «мозг» продукта. Из документов, которые собрал P2, ты извлекаешь **проверенные сигналы с цитатами** и
считаешь **объяснимый скор**. От тебя напрямую зависят два самых весомых критерия жюри: точность сигналов (25%) и
AI/ML-инновации (20%).

| Отвечаешь за | Где |
|---|---|
| Граф LangGraph: resolve → collect → index → prefilter → extract → verify → score | `backend/ai/src/leadradar_ai/pipeline/` |
| LLM-шлюз Gemini: structured output, лимиты, fallback-модели, кэш | `llm/` |
| Префильтр: нарезка, эмбеддинги, BM25 + векторы | `retrieval/` |
| Промпты и примеры | `prompts/` |
| Проверка цитат кодом | `verification/` |
| Формула скоринга | `scoring/` |
| Пресеты услуг IA и Cybersecurity | `presets/*.yaml` |
| Замер качества: золотой набор, precision / recall | `evals/` |

**Не твоё:** БД и API (P1 — ты работаешь через порты), сбор данных (P2). Пакет `ai` не импортирует `parser`, `core`, `auth`.

## 3. Как работает анализ (что именно ты строишь)

```
документы компании (от P2 через P1)
  → index:     нарезка на фрагменты 120–220 слов + эмбеддинги multilingual-e5-small (локально, на CPU)
  → prefilter: для каждого вопроса BM25 + векторы → RRF → 5 лучших фрагментов; отсев чужих компаний и старья
               итого ≤ 40 фрагментов на услугу
  → extract:   ОДИН вызов Gemini на услугу: ответы на все вопросы + дословные цитаты (JSON по схеме)
  → verify:    код проверяет: цитата реально есть в тексте? про эту компанию? свежая? иначе — выбросить
  → score:     формула Fit × Intent × (1 − Risk) → Priority, Tier, «почему сейчас»
```

**Почему так.** Бесплатный тариф Gemini даёт мало запросов в сутки, поэтому один вызов на услугу, а не на каждый вопрос.
LLM только извлекает факты, считает код. Поэтому результат воспроизводим, объясним и мгновенно пересчитывается при
смене весов.

## 4. Правила промптинга Gemini (обязательно)

- Роль, правила и формат ответа — в **system instruction**. В user-сообщении сначала данные (компания, услуга,
  фрагменты), потом вопросы, а задача — в самом конце.
- Разделители — XML-теги (`<snippets>`, `<questions>`), один формат везде.
- В каждом промпте есть **few-shot примеры** той же структуры, что и ответ. Обязательно с ловушками: компания-вендор,
  омоним, новость про партнёра.
- **`temperature` у Gemini 3.x не трогать** — Google предупреждает о зацикливании. Детерминизм дают схема, проверка и кэш.
- Ответ — строго по JSON-схеме (Pydantic → `response_schema`).
- Можно отвечать `unclear`: лучше промолчать, чем выдумать.
- Любая правка промпта → новая версия (`extract_signals@v2`), затем прогон evals.

Каркас промпта — [backend/ai/SPEC.md](../../backend/ai/SPEC.md) §1.7.3.

## 5. Точность (главный критерий жюри)

| Мера | Против какой ошибки |
|---|---|
| Фильтр сущности в префильтре | новости про другую компанию с похожим названием |
| Правило 4 в промпте + правило «вендор» | компания сама продаёт автоматизацию — это не сигнал покупки |
| Дословная цитата + проверка кодом (точное или нечёткое совпадение ≥ 90) | выдуманные факты |
| Окно свежести на вопрос + полураспад | старые события |
| Рубрика силы: weak / moderate / strong | маркетинговая вода как сильный сигнал |
| Не больше 3 доказательств на вопрос | одно событие в 10 новостях считается 10 раз |
| Негативные вопросы (сильный свой CoE, текущий партнёр) | переоценка компаний вроде Lufthansa и DHL (Annex) |

**Замер.** Золотой набор `evals/golden/mvp.jsonl` — ≥ 100 меток по ≥ 10 компаниям, обязательно Lufthansa и DHL.
Цель — precision ≥ 0.8 по ответам `yes`. Фидбек продажников из UI (✓ / ✗) — вторая метрика, её считает P1.

## 6. Формула скоринга (кратко)

```
вклад доказательства v = сила × уверенность × надёжность источника × 0.5^(возраст / полураспад)
сила вопроса        s  = 1 − Π(1 − v)                       # несколько подтверждений усиливают
Intent = 100·(1 − e^(−Σ вес·s / 3))     Risk = 100·(1 − e^(−Σ вес·s негативов / 2))
Fit    = доля совпавших критериев ICP (must-have провален → 0)
Priority = 100 · (Fit/100)^0.4 · (Intent/100)^0.6 · (1 − 0.5·Risk/100)
```

Все параметры — в `ScoringProfile`, админ меняет их в UI. Функция чистая, без LLM. Обязательны тесты с конкретными числами
и свойства: больше позитива → скор не падает; больше негатива → не растёт; старее → вклад меньше.

## 8. Бюджет квот Gemini

- ≤ 2 вызова на пару «компания — услуга», в среднем 1.
- Нет кандидатов у вопроса → ответ `no` без вызова. Нет новых фрагментов → извлечение пропускается (fingerprint).
- Кэш ответов: повторный прогон в разработке квоту не тратит.
- 429 → ждать → следующая модель пула → `QuotaExhausted` (компания на паузе, продолжение с чекпоинта).
- Пакетный прогон 40–60 демо-компаний начинать **не позже H24**. Сутки квоты начинаются в 10:00 по Кишинёву.

## 11. Частые ошибки

- Просить LLM посчитать скор — невоспроизводимо и необъяснимо. LLM только извлекает.
- Вызов на каждый вопрос или отправка документа целиком — квота кончится к обеду.
- Доверять `confidence` модели без проверки цитаты кодом.
- Правила, которые может выполнить код (даты, пороги, списки клиентов), — в промпте.
- Большие тексты в состоянии графа → раздутые чекпоинты. В состоянии только id и кандидаты.
- Правка промпта без новой версии и без прогона evals.
